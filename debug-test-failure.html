Raft Leader Failover Test Race Condition Analysis

Problem Summary

Test: MetadataClientLeaderFailoverTest#testConnectionFailureTriggersFailover

Symptoms: Intermittent failure where Object 2 returns null (expected: not ) after leader failover

Failure Rate: ~40% (2 out of 5 runs)

Error Message: org.opentest4j.AssertionFailedError: Object 2 should be accessible ==> expected: not

Root Cause

Sequence of Events Leading to Failure:

T1
Object 2 CREATE: Client submits entry to new leader
• Entry appended to Raft log
• Committed by majority
• Commit future completes IMMEDIATELY
T2
Background apply loop: Runs every 10ms
• Checks for entries where commitIndex > lastApplied
• Applies entries to state machine
• Advances lastApplied
RACE WINDOW
T3
Object 2 GET: Client immediately requests Object 2
• GET arrives at new leader
• MetadataStore.getObject() checks database
• Entry NOT YET APPLIED (still in Raft log)
• Returns null → TEST FAILS
T4
Background apply runs: Finally applies Object 2 entry
• Object 2 now in MetadataStore
• Subsequent GET would succeed
TOO LATE!

Key Issue: Asynchronous State Machine Application

The commit future now completes after state machine application (moved from updateCommitIndex() to applyCommittedEntries()), but in multi-node clusters:

  • Entries are applied by the background loop (every 10ms)
  • Client receives success when commit future completes
  • But entry may not be applied to state machine yet
  • GET request races with background apply loop

Previous Fix Attempt

Code Changes Made:

// OLD: Completed future immediately on commit if (replicationCount >= majority) { raftLog.advanceCommitIndex(index); CompletableFuture future = pendingCommits.get(index); if (future != null) { future.complete(true); // <-- HERE: Immediate completion } } // NEW: Wait for apply before completing future if (replicationCount >= majority) { raftLog.advanceCommitIndex(index); // Do NOT complete the commit future here // Wait for applyCommittedEntries() }
// In applyCommittedEntries(): stateMachineApplier.accept(entry); raftLog.advanceLastAppliedTo(entry.index()); // Complete future AFTER apply CompletableFuture future = pendingCommits.get(entry.index()); if (future != null) { future.complete(true); // <-- HERE: After apply System.out.println("[RAFT] ... after apply"); }

Why this didn't fully fix it: The background apply loop runs asynchronously every 10ms. When client immediately sends GET after CREATE returns, it might arrive before the background loop runs.

Proposed Solution

Option 1: Synchronous Apply for Multi-Node Too

1
Modify RaftNode.submit() for multi-node
In the multi-node path, after replication to majority, synchronously apply the entry before returning success
2
Handle background loop conflict
Use the same applyLock mechanism to prevent double application of entries by both submit path and background loop
3
Update test expectations
Test already expects Object 2 to be immediately accessible - this fix makes that guarantee stronger

Option 2: Add Retry Logic in Client

1
Modify ClusterMetadataClient.getObject()
Add retry with exponential backoff when Object 2 returns null but CREATE succeeded
2
Track known committed objects
Maintain a set of object names that CREATE succeeded for, retry GET if object missing

Recommended Implementation

// Add to RaftNode.submit() multi-node path: boolean committed = commitFuture.get(10, TimeUnit.SECONDS); if (committed) { // NOW synchronous: apply before returning synchronized (applyLock) { // Check if entry was already applied by background loop if (raftLog.getLastApplied() >= index) { System.out.println("[RAFT] " + nodeId + " entry " + index + " already applied"); } else { // Apply synchronously stateMachineApplier.accept(indexedEntry); raftLog.advanceLastAppliedTo(indexedEntry.index()); System.out.println("[RAFT] " + nodeId + " applied entry " + index + " synchronously"); } } } return committed;

Advantages:

  • Strong consistency: CREATE returns success only after entry applied
  • No test modification needed: Already expects Object 2 to be accessible
  • Simpler: Single code path for both single and multi-node
  • Correct Raft semantics: Entry is durably applied before client receives success

Considerations:

  • Performance: Synchronous apply may add latency for multi-node operations
  • Lock contention: applyLock may block background loop
  • Need to check background loop: Ensure it doesn't double-apply entries

Testing Strategy

  1. Run focused test 10 times: Verify fix eliminates intermittent failures
  2. Run all MetadataClientLeaderFailoverTests: Ensure no regression
  3. Run metadata-server tests: Verify Raft implementation correctness
  4. Full mvn clean test: Overall system validation

Success Criteria:

  • Test passes 100% of time (10/10 runs)
  • All Raft tests pass without modification
  • No performance regression in multi-node operations
  • Correct Raft semantics preserved: entry applied before success returned
