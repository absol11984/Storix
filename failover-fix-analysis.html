Key Issue: Client's executeWithLeaderRouting Logic

When invalidateLeaderCache() clears the cache, executeWithLeaderRouting() may connect to a follower that doesn't have the data yet. The routing logic doesn't account for replication lag.

Solution Options

Option 1: Wait for Replication in CREATE

Fix Raft replication to wait for entry to be applied on followers before returning success.

  • PRO: Strong consistency guarantee
  • PRO: No client changes needed
  • CON: Increases CREATE latency
  • CON: More complex Raft logic

Option 2: Retry in GET

Modify client GET logic to retry with short delay when object not found after recent CREATE.

  • PRO: Simple implementation
  • PRO: Works with existing Raft
  • CON: Increases GET latency
  • CON: Requires client modification

Option 3: Better Leader Cache

Improve client leader caching to avoid clearing cache unnecessarily and track which server accepted recent writes.

  • PRO: Minimizes routing to followers
  • PRO: No Raft changes needed
  • CON: Complex client state tracking
  • CON: Still possible to hit follower

Recommended: Option 1 (Strong Consistency)

Raft should guarantee that once CREATE succeeds, subsequent GET from the same client will see the data. This is the expected semantics for a consensus system.

Implementation Plan (Option 1)

Fix 1: Ensure synchronous application on multi-node

In RaftNode.submit(), after entry is committed by majority, ensure it's applied synchronously before returning success.

// In submit() method, after commitFuture.get(): if (committed && stateMachineApplier != null) { synchronized (applyLock) { if (raftLog.getLastApplied() >= index) { // Already applied by background loop } else { // Apply synchronously stateMachineApplier.accept(indexedEntry); raftLog.advanceLastAppliedTo(index); } } } return committed;

Fix 2: Replicate to majority of followers before success

Wait for entry to be replicated to a majority of followers, not just committed on leader.

Fix 3: Test strategy update

Test should verify Object 2 is immediately accessible after CREATE succeeds.
